# Supervisor and relay isolation

The production scheduled task runs from the digest-addressed Supervisor Runtime store beneath the existing Operations local application directory. Its working directory is that immutable runtime. The Managed Releases store holds worker versions, the active pointer, the verified previous release and the handover journal. Worker staging can populate only Managed Releases. It cannot replace the supervisor. Keep the launch environment and device credential in their existing operational locations.

Prepare each supervisor candidate out of a specific Git commit with `node tools/operations-worker/prepare-supervisor-runtime.mjs <absolute-checkout> <commit> <absolute-existing-candidate-directory>`. The candidate directory must be outside the checkout. Keep the printed commit and manifest digest as release evidence. Test the candidate in a disposable process with loopback endpoints and its own runtime configuration and data directories. Never copy production credentials into test configuration.

For a legacy installation still pointing at a Git worktree, prepare the supervisor code from the last known working commit first. Run `Switch-ManagedSupervisorRuntime.ps1 -Candidate <digest-directory> -ManifestSha <reviewed-digest>` to verify the candidate without changing the scheduled task. During an owner-authorized, held and drained maintenance window, execute the same command with `-Apply` to install, repoint and verify it. The script retains the active worker release identity and restores the prior task action if fresh authenticated readiness fails. Preserve the previous supervisor candidate and the known-good worker bundle for recovery. Verify hosted heartbeat, reconciliation and disposable dispatch before restoring admission.

Install new managed deployments with independently reviewed worker and supervisor bundles. Normal worker updates continue through the hosted worker lifecycle. Supervisor updates always use the separately governed supervisor handover.

Windows workspaces provide a scoped code-execution boundary for standard assignments. Production runtime directories are outside those writable roots. The installed supervisor and the owner's unrestricted session may still run under the same Windows account. The owner must explicitly authorize maintenance work in that context. A future operating-system account boundary can provide stronger protection against a deliberately unrestricted process.
